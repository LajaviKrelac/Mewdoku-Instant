## How to file a request

- Use this file when you need a change in a file you do not own (spec §8.1): anything outside `server/**`, `src/shared/rank-api.ts` and `tests/unit/shared/**`. Do not edit that file yourself. A file the table does not list is the lead's (root `package.json`, `tsconfig.json`, `vitest.config.ts`, `playwright.config.ts`, `scripts/**`): ask here first.
- One row per request: the next number (R1, R2, …), from → to (G1, G2, G3 or lead), the file and the exact change, and why (the spec or contract section). A wire change you make yourself (`src/shared/rank-api.ts`, the fixtures) still gets a row here with the client impact stated, so G1 and G3 see it; fields stay additive inside v1.
- The receiving workstream notes what it did in its own file, under "Done for other workstreams' requests", and marks the row here **done by …**. The lead answers anything still open at I-2.

- **Golden fixtures:** `server/test/contract/fixtures/<endpoint>.<case>.json`, each `{ name, request: { method, path, auth?, body? }, response: { status, body } }`: `health.ok`, `config.ok`, `nonce.ok`, `session.fb`, `session.web`, `wins.ok`, `wins.mixed` (duplicate, accepted_flagged/unverified, rejected/too_fast, already_counted), `bracket.open` (3 rows), `bracket.none`, `bracket.alone` (1 row), `bracket.full` (50 rows), `bracket.ended` (final, with a paid result), `claim.ok`, `claim.already`, `hearts.ok`, `profile.nickname`, `profile.listed`, `me.ok`, `me.delete` (204, body null) and one `error.<code>` per `ErrorCode`. Every fixture body parses to itself with the shared parsers (`tests/unit/shared/rank-api.spec.ts`), and the server's own tests check that its real answers have the same shape. G1's `tests/fixtures/ladder-fake.ts` can read them with `fs` (they are data; the root tsconfig never imports `server/**`).
- **Client rules the parsers already apply** (CONTRACTS §2.2, C-34): a row that fails its check is dropped and `members` stays the server's number; a view with more raw rows than `maxMembers`, duplicate slots or ranks, a rank above `members`, an invalid `me`, or `state: 'none'` with a bracket id (or the reverse) is rejected whole; unknown verdicts drop that win's result (the win stays queued), unknown reasons are dropped from their result; `parseConfigResponse` keeps booleans of `REMOTE_SWITCHES` only.
- **S1 running (dev server):** `npm --prefix server run dev:node -- --port 8787` answers the whole API v1 (session/nonce, session fb + web anon, wins, bracket, claim, hearts, profile, me, delete) plus `/dev/clock` `{devPool, advanceMs | offsetMs}`, `/dev/reset` `{devPool}`, `/dev/config` `{devPool, switches}` and `/dev/cron` `{devPool}` (finalise due brackets at that pool's time). Test players are made only through the public API (H-1). Dev secrets (public test values, see `server/dev/serve.ts` `DEV_DEFAULTS`): FB `e2e-fb-app-secret` (CONTRACTS §5, the stub's default), admin key `mewdoku-dev-admin-key-0123456789abcdef0123456789` (for the e2e "suspended player" test: `POST /admin/v1/players/<code>/suspend` with `Authorization: Bearer <admin key>`).
- **Server behaviours the client sees** (all within CONTRACTS §2/§3): tokens last 24 h of the player's pool clock, so a `/dev/clock` jump of ≥ 24 h makes the next call 401 `token_expired` (sign in once more, as in production); a bracket is finalised 30 s after `endsAt` (`bracket.finalizeGraceMs`), so right at `endsAt` the view is `state: 'ended', final: false, result: null`, and once final it carries `result`; a finalised view's `members` is `final_members` (the count ranked at the end), so after a later deletion or suspension its `rows.length` can be smaller with a gap in the ranks (the parsers keep it: "shown as sent"); `WinsResponse.bracket` is null when I have no bracket; `windowPoints` is my points while the bracket is open, else 0; rejected wins are not stored, so re-sending one is judged again (normally the same verdict); a retried accepted win answers `duplicate` with its original points.
- **Clocks in e2e (G1):** FB signatures and nonces are checked on real time, tokens and all game logic (brackets, the daily window, claims) on the pool's clock. The stub signs `issued_at` with the browser's clock, so a test that installs `page.clock` at another time must move its dev pool by the same amount first: `POST /dev/clock {devPool, offsetMs: <page time − Date.now()>}`; inside a test pool the server then accepts `issued_at` on either clock (never in the real pools). `/dev/cron {devPool}` finalises that pool's due brackets at its own time (no stats, no sweep), for result-card tests after a clock jump of ≥ 24 h 30 s.
- **Unexpected server errors** (a D1 failure, the Free plan's per-invocation query limit in the rare lost-join retry of a ten-win batch) answer 503 `unavailable` with `retryAfterMs` 30 000 and write nothing; the wins stay queued (CONTRACTS §3 back-off).
- **Request shape bounds** (`isWinSubmission`, shared by the saved queue and the server, so a queued win that passes is never a 400): `fish` 1…20 (the server applies 3 or the event's lives), `mistakes` 0…99, `revives` 0…9 (the server applies 1), helpers 0…999, `solveMs` 0…2³¹−1, `contentVersion` `CONTENT_VERSION_RE`, `clientVersion` `CLIENT_VERSION_RE` (`0.2.0`, `0.0.0-test`). `validateProfileRequest` checks the shape only (the word-list bounds, `NICK_NUM_MIN…MAX` and `avatarId < AVATAR_COUNT` are the server's 422s) and needs at least one field.
